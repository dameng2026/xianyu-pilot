# 自动发货产品标准与当前实施优先级

确认日期：2026-10-29。适用范围：本仓库正在建设的 Windows 本地桌面工作流。

> **实施方式已于同日修正：在原项目已有功能上增量修改。** 后续使用 `apps/web` 原后台和 `apps/api` 原自动发货、订单、货源库、卡密仓库及回执流程，不另建独立演示业务系统。下文涉及 SQLite 桌面工作流、四页重组和另做卡密库存的描述保留为历史方案，不再作为后续实施顺序。直接发货优先、QQ 按需启用、库存与回执防重复等产品原则继续适用。当前实施记录见 [原系统自动发货增量改造](auto-delivery-incremental.md)。

本文记录本轮确认的产品方向。既有 QQ 整合方案中与此方向冲突的优先级，以本文为准；本文描述的目标不代表功能已经完成。当前运行方式见 [本地工作流说明](desktop-demo.md)。

## 1. 产品定位

产品的核心用途是帮助闲鱼卖家自动发货。用户配置商品发货规则后，系统根据付款订单准备交付内容、发送给买家、确认平台发货，并跟踪失败和人工处理。

QQ 是部分商品需要的可选处理服务。用户可以完全不配置 QQ，完成直接发货流程。MCP 是对客户端开放业务工具的可选入口，普通卖家操作和自动发货调度均不依赖 AI 或 MCP 客户端在线。

当前部署要求为 Windows 本机运行，无需 Docker。本地工作流使用 Vue、FastAPI 和 SQLite。

## 2. 已确认的产品标准

### 2.1 直接发货作为默认路径

- 新建商品默认选择直接发货；创建任务默认继承商品规则。
- 首版发货内容覆盖固定文字、链接、教程，以及按订单分配的独立卡密。
- 自动执行或卖家确认后执行，由商品策略决定；选择直接发货不等于强制立即执行。
- 没有 QQ 账号、服务或连接器时，商品配置、订单处理和直接发货均可使用。
- 只有主动选择“需要外部处理”时，才展示对应服务和参数配置。

### 2.2 QQ 按需启用

- QQ 账号属于用户本人，供应商不提供、不代持、不共享账号，也不提供统一 QQ 池。
- 当前阶段不登录真实 QQ，不安装 Tulpa，不继续投入真实 QQ 接入联调。
- 现有 QQ 服务、模拟验证和任务扩展结构保留，不能因其异常阻断独立的直接发货任务。
- QQ 配置应归入可选集成设置。使用该服务的商品和任务才展示相关状态、参数和请求记录。
- 未来确有商品需要时，再接入用户明确选择的连接方式；MCP 本身不承担 QQ 登录和消息传输。

### 2.3 商品存默认规则，任务保存快照

- 商品配置包含处理方式、发货内容来源、模板、执行策略和平台发货确认策略。
- 创建任务时保存当时规则及版本；有外部处理时，同时保存服务和账号引用等必要配置，不复制账号密钥。
- 后续修改商品规则不改变已有任务。
- 执行前可以显式修改任务处理方式、模板或本工作区服务，保留修改记录并重新确认。
- 外部请求已提交、卡密已发送或买家已收到内容后，不能通过“取消”宣称撤销已发生的动作。

### 2.4 交付和平台确认发货分开

直接发货主流程：

1. 接收并核实付款订单。
2. 匹配商品规则，去重创建任务并保存快照。
3. 准备固定内容，或为订单预留卡密。
4. 根据策略等待卖家确认或自动执行。
5. 向买家发送内容，记录发送结果。
6. 交付成功后，按策略自动确认或等待人工确认平台发货。
7. 两个步骤都完成后，任务才标记为完成。

界面必须区分模拟回执、人工记录和真实平台回执。买家消息发送成功不能直接代表平台已经确认发货；人工填写“已付款”也不能代表收到真实付款事件。

### 2.5 幂等、库存与异常处理是主线要求

- 订单去重键由工作区、卖家账号和平台订单标识共同确定；重复通知不能重复创建任务、分配卡密或发货。当前本地登记键只覆盖工作区内订单编号，真实平台适配时需补齐账号维度。
- 交付、平台确认发货分别保存稳定操作编号、尝试记录和回执。
- 卡密至少区分可用、已预留、已交付、待核对；同一卡密不能分配给不同订单。
- 同一任务再次执行不能默默换一张卡密。库存不足时转待处理，并提示补充库存。
- 明确未发送的失败可以按规则重试；请求发出后结果不明、超时或崩溃恢复时，先核对，不能盲目重发。
- 结果不明的卡密继续占用并标记待核对，不能自动释放给其他订单。
- 仅在能够确认尚未发送时，取消任务才可释放预留卡密；已经发送的卡密不能重新作为可用库存。
- 平台确认发货失败时，只重试或人工处理该步骤，不能因此再次发送卡密。
- 补发必须明确发起并记录原因、内容和关联任务，不能等同于普通失败重试。

## 3. 页面目标

| 入口 | 核心内容 |
| --- | --- |
| 发货工作台 | 待发货、成功、失败待处理、库存不足；任务详情、步骤回执和人工操作 |
| 商品与发货规则 | 默认直接发货；固定内容或卡密；执行和平台发货确认策略 |
| 发货内容与库存 | 固定内容模板、卡密导入与去重、库存状态、分配和交付记录 |
| 设置与可选集成 | 本地运行、闲鱼连接配置；按需配置 QQ 服务和 MCP 授权 |

这是接下来的页面调整目标。目前界面仍是 QQ 账号、QQ 服务、商品配置和任务工作台四个页面，尚未完成上述导航重组。

## 5. 现在最应该做的事情

**优先完成“不配置 QQ 的直接发货最小闭环”，先通过本地模拟验收，再接真实闲鱼。**

### 第一步：调整使用入口，验收固定内容发货

将默认入口转到发货工作台，QQ 和 MCP 移到可选集成。以一个固定教程或链接商品为样例，从新工作区开始，不配置任何 QQ 或 MCP，完成商品配置、订单登记、规则快照、模拟交付和模拟确认发货。

此步复用现有能力，重点验证主流程独立、状态清楚、失败可处理，避免继续扩展 QQ。

### 第二步：补齐卡密库存与交付分配

在 SQLite 工作流内实现导入去重、库存状态、订单预留、交付记录和待核对处理。订单预留必须在事务中完成，重复触发和并发处理都不能重复分配。

最低验收场景：

- 一份教程可以交付多笔不同订单；同一订单重复通知只产生一个任务。
- 两笔订单分配不同卡密，同一订单重复处理不消耗第二张。
- 库存不足时停止该订单的发货并提示补货。
- 消息发送成功而平台确认发货失败时，不重复发送内容。
- 发送结果不明或程序重启时，保留原内容和预留关系，转人工核对。
- 修改商品模板后，已有任务仍按原快照执行。
- 所有测试均无需 QQ 账号，模拟结果均有明确标识。

### 第三步：接入真实闲鱼并小范围验证

先梳理旧版付款事件、订单查询、消息发送和确认发货能力，确定适配方案。将这些能力接到同一套任务和回执机制，避免另建一套发货状态。

真实账号接入及实际发送另行明确范围；开发和模拟测试不代表已授权发送真实消息或执行真实订单发货。首次联调先核实订单与付款状态，再进行明确范围内的交付和平台确认。

## 6. 本阶段暂缓事项

- 真实 QQ 登录、连接器安装与联调。
- 以 QQ 为中心继续增加页面或能力。
- 复杂流程编排、跨 QQ 账号自动切换、供应商账号池。
- 为自动发货引入强制 AI 或 MCP 依赖。
- 在核心发货闭环未验证前，扩展复杂计费和多租户 SaaS 体系。
