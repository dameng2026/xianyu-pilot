## 1. 先明确最终做成什么

首版交付一个 Windows 本地桌面软件，完成：

> 连接一个闲鱼账号 → 绑定一个商品和一个 QQ 好友机器人 → 接收符合条件的查询 → 持久化排队 → 向固定机器人发送文字 → 确认结果归属和完整性 → 回给原闲鱼买家 → 保存操作回执。

同时提供连接状态、任务列表、暂停、异常核查、退出和重启恢复。

首版限定一个闲鱼账号、一个 QQ 账号、一个好友私聊机器人、文字查询、QQ 通道并发为 1。群聊、图片语音、多机器人、复杂运营、RAG 和手机管理后置。付款后服务作为独立开关，只有订单核验通过才可启用。

开发环境可以有 Python、Node、MySQL、Redis；最终用户安装包不得要求用户自行搭建这些开发环境。两者是不同验收对象。

## 3. 技术方案先固定

### 3.1 运行结构

采用两个本应用进程：

1. 桌面窗口进程：pywebview 承载 Vue 构建产物，负责窗口、托盘和用户操作。
2. 本地业务宿主：承载 FastAPI、闲鱼连接、QQ 单通道执行器和任务恢复；是业务数据库的唯一应用写入宿主。

QQ 第三方组件和按需浏览器另行管理，不计为“已经消除”的依赖。两个本应用进程之间使用受控 IPC 传递启动状态与凭据，不通过命令行参数传递密钥。

首版选择本机 HTTP 承载静态页面和 API，默认只监听 `127.0.0.1`。由宿主管理端口与监听生命周期，保留受认证的实时事件通道。打包后的页面与 API 尽量同源，避免 `file://` 与宽泛 CORS 兼容方案。

### 3.2 存储与目录

- 业务存储：SQLite，使用 `aiosqlite` 驱动并保留 SQLAlchemy 的可复用部分。
- 可靠事实：任务、回执、授权撤销、额度、租约写数据库。
- 临时缓存：有容量与过期时间的内存缓存。
- 凭据：随机数据密钥由 Windows 当前用户范围 DPAPI 保护，敏感正文写盘前 AES-GCM 加密。
- 应用文件：`%LOCALAPPDATA%\Programs\XianyuPilotDesktop`。
- 用户数据：`%LOCALAPPDATA%\XianyuPilotDesktop`。
- 数据目录内部再区分数据库、密钥封装、日志、缓存、备份；不写源码目录。

### 3.3 首版默认行为

- 新绑定默认未启用自动查询、未启用自动交付。
- 首次运行不自动发消息。
- 暂停阻止新的外部操作，保留对已经发送任务的必要回执接收。
- 无可靠关联依据时，超时冻结 QQ 通道，不继续派发下一单。
- 桌面不默认运行旧商业桥接、广告、反馈、自动评价、重新上架和外部模型请求。
- server 配置继续默认使用 MySQL/Redis；故障不能自动切 SQLite。

### 6.2 连接器契约

定义 `health / capabilities / submit / receive / reconcile / close`，业务层只依赖这组接口，不直接调用 Tulpa 任意工具。

- `health` 返回实际登录账号、目标会话和绑定核验状态。
- `submit` 接收由绑定解析出的固定目标与已校验请求，返回 `confirmed_sent / definitely_not_sent / unknown` 等明确语义；不能只返回布尔成功。
- `receive` 返回来源账号、会话、发送者、平台消息 ID、引用/关联信息和必要正文。
- `reconcile` 使用原操作编号核查，不能自动换编号重发。
- `close` 停止连接，不能声称撤回已发送消息。

策略测试必须验证：请求参数不能覆盖目标 QQ；机器人返回的文字不能修改设置或触发其他工具。

### 6.3 Mock 的边界与验收

先用纯逻辑测试跑通虚构请求和结果，不加载 `app.main`、全局数据库或真实 QQ。这个阶段可使用内存测试对象，但不将其作为生产队列，也不声称已经支持重启恢复。

完成条件：正常结果可匹配；重复事件可识别；其他发送者被过滤；无关联的迟到结果不归入下一任务；发送拒绝与发送不明是不同错误。持久化与崩溃恢复在 S03/S04 验收。

逐项处理：

| 问题 | 实现要求 |
| --- | --- |
| `BigInteger` 自增 | 使用 SQLite `INTEGER` 主键变体并验证插入、引用和回读 |
| `NOW()`、`DATE_SUB` 等 | 仓储内适配或使用明确的 UTC 应用时间，不全局替换字符串 |
| `FOR UPDATE`、`GET_LOCK` | 用短事务、条件更新、唯一约束与租约；核验更新成功数量 |
| MySQL 同步访问 | 将 `pymysql.connect` 相关数据读写移到可注入仓储，保留可复用 HTTP/签名逻辑 |
| JSON、默认值、索引与约束 | 用真实 SQLite 驱动验证，不能只看 SQLAlchemy 模型可导入 |
| 多后台任务写库 | 单业务宿主管理写入，事务内不等待 QQ、闲鱼或浏览器 |
| 持久运行 | 核验 WAL、外键、busy timeout，清理使用有界批次 |

### 8.3 凭据与安全状态

新增 `desktop_credentials.py`、`desktop_security.py`、`security_state.py` 和桌面实现。

1. 安装首次生成随机数据密钥，DPAPI 封装后保存于受限数据目录。
2. 将密钥提供器接入 Cookie 加密及通用敏感字段加密；不同用途绑定不同认证上下文。
3. 解密失败、密钥缺失或损坏时暂停业务并显示修复入口，不自动生成新密钥覆盖。
4. Redis 的登录计数、Token 撤销和额度改用 SQLite 原子持久实现；缓存单独处理。
5. 桌面 UI、可选业务 MCP、第三方 QQ 连接分别使用不同权限凭据。
6. UI 启动通过受信窗口桥接/IPC 完成一次性会话建立，不把长期 Token 放 URL、日志或命令行。具体会话协议在编码前写入安全设计并完成测试。
7. 本机 API 验证认证、Host、Origin、请求大小；静态资源、健康检查和会话建立端点分别列出允许范围，不使用全局通配 Origin。
8. SSE 沿用经审查的短期票据或受保护会话；不能把长期管理 Token 放查询串。

### 8.4 最小宿主启动与验收

顺序：单实例锁 → 私有目录/空间检查 → 解锁凭据 → 受控迁移 → 本机 API → 连接器接收 → 恢复扫描 → 就绪。

此阶段仅加载最小受保护状态接口与 Mock，不开放未适配的闲鱼旧接口。必须在 MySQL/Redis 不可用的隔离环境下启动成功；server 模式仍按原规则拒绝错误配置，不能降级。

窗口与完整安装器留待 S06/S07，但单实例、进程归属和有序退出现在就要实现，不能拖到打包时补。

## 9. S04：实现持久 QQ 任务与固定目标网关

### 9.1 待新增业务模块

在 `services/qq_bridge/` 下增加 `task_service.py`、`channel_runtime.py`、`recovery.py`、`delivery_adapter.py`。仓储放 `storage/desktop/`，真实 MCP 适配放 `client_tulpa.py`。

业务与连接器分离：策略决定允许做什么，任务服务决定状态，连接器只执行经过校验的操作。可选的对外业务 MCP 留到核心业务稳定后，不作为第一条闭环的前置依赖。

### 9.2 数据最小要求

| 记录 | 至少承担的职责 |
| --- | --- |
| 绑定 | 固定闲鱼商品、QQ self ID、机器人 ID、会话、模板、策略版本、启停与核对状态 |
| 任务 | 来源事件键、来源买家/会话、绑定与策略快照、加密输入/结果、状态、截止时间 |
| 外部尝试 | 阶段、稳定操作编号、尝试代次、回执、是否明确可重试 |
| 入站事件 | 已过滤来源、平台消息 ID、关联信息、必要加密正文与去重键 |
| 通道 | 当前任务、租约、递增 fencing token、冻结原因与读取进度 |
| 策略审计 | 绑定、撤销、人工核查与恢复决定，不记录凭据 |

来源事件和绑定建立唯一约束；相同来源重放返回已有任务。改变策略版本不能自动绕过来源去重。手动请求使用稳定 `client_request_id`，同编号不同输入必须报冲突。

### 9.3 状态与操作边界

```text
queued → qq_sending → waiting_reply → result_ready → delivering → completed
```

补充分支为 `failed_safe / unknown / cancelled / paused_policy`。

1. 短事务领取 queued，校验身份与策略，原子占用通道并写 qq_sending，提交后再调用 QQ。
2. 回执确定发送成功才进入 waiting_reply；明确未执行可进入 failed_safe；结果不明进入 unknown。
3. 接收事件先过滤账号、会话、发送者，再必要落库、去重；确认本地持久化后才推进上游读取确认。
4. 结果必须有归属和完整性证据，保存加密结果后进入 result_ready。
5. 闲鱼交付有独立边界和回执；交付失败不重新查询 QQ。
6. 所有状态写回校验当前状态、租约与 fencing token；旧执行者不能覆盖新持有者。
7. 业务超时与工作租约分别处理。等待网络期间不持有写事务；执行者的所有权续租使用短事务。

### 9.4 重启恢复规则

| 恢复时状态 | 允许操作 |
| --- | --- |
| queued | 重新校验后领取 |
| qq_sending 且租约失效 | 转 unknown，禁止自动重发 |
| waiting_reply | 恢复接收和核查回执/事件缺口，不重新发送 |
| result_ready | 仅推进闲鱼交付 |
| delivering 且回执不明 | 交付阶段 unknown，不再次查询或发送 |
| completed | 返回已有结果 |
| paused_policy | 等用户核对原任务，不自动改绑 |

无编号/引用时，单通道只是必要条件。任务超时或事件有缺口后冻结通道，不能因下一条消息到达就归给下一买家。安静若干秒只作候选完成依据，未经真实验证不能自动交付。

### 9.5 验收

用真实 SQLite + Mock 完成重复提交、并发领取、重复回复、错误来源、迟到结果、策略撤销、发送不明、写回失败和重启测试。模拟注入至少 1,000 个任务，检查资源有界和顺序正确。真实 QQ 不用于压力测试。

## 10. S05：接入闲鱼，先一条闭环再扩展

### 10.1 先适配账号连接与收发依赖

逐条跑通：扫码产生会话 → 获取并加密保存凭据 → 显示实际账号 → 获取/刷新 Token → WebSocket 注册 → 收消息 → 发送文字并验证确认 → 重启恢复连接。

重点改造 `core/xianyu_qr_login.py` 的调用方、`ws_token.py`、`ws_client.py`、`cookie_token_refresher.py`、账号路由和必要聊天存储。协议解析尽量保留，数据库访问迁入仓储。逐项检查同步 HTTP 调用是否阻塞业务事件循环，必要时受控放入线程执行。

登录、刷新、消息三个环节都通过 SQLite 才算完成，不能以扫码页面出现作为接入成功。

### 10.2 建立唯一业务路由

在 `ws_startup.py` 消息持久化入口和 Outbox 分派处增加 QQ 路由，建议新增 `qq_bridge/source_router.py`。

明确选择：对于匹配有效 QQ 服务绑定的来源事件，持久化 QQ 分支；普通消息维持原有 AI/发货策略。QQ 管理的商品必须让旧自动回复、实时发货和补发扫描识别相同服务归属，避免通过另一条后台路径重复处理。

路由决定与消息/Outbox 在同一事务提交，至少保存所选绑定与策略版本的不可变引用。可扩展原 Outbox 字段或使用关联路由记录，具体设计需形成一个统一方案，不在各回调里临时判断。

Outbox 领取后调用幂等的 `task_service.create_from_source`；即使在任务提交后、Outbox 确认前崩溃，也只返回已有任务。分派时重查撤销状态，不能仅信任入队时允许。

server 若要启用新 QQ 分支，必须新增下一条 MySQL 正向迁移并验证；如果首版仅开放 desktop，则 server 保持旧功能集并拒绝启用 QQ，不为未使用功能擅自改生产数据库。

### 10.3 普通查询先通过

路径：买家对已绑定商品发送有效输入 → 后台从已验证来源提取商品/会话 → 校验字段、额度和绑定 → 创建任务 → QQ 查询 → 匹配 → 保存结果 → 回原会话。

商品/买家/会话身份不能从自由文本中指定。普通问候、卖家自身消息、重复消息、无关商品不得创建查询任务。

### 10.4 再开启付款后服务

新增 `qq_bridge/order_eligibility.py`，负责实际订单归属、商品、买家、状态与可用次数核验。

- 付款提醒只触发订单同步，不能直接充当付款证明。
- 用可信订单状态校验资格，原子占用本次服务次数。
- 多次服务使用独立兑换序号；同一订单的不同通知不能各生成一份服务。
- 提交 QQ 前复核必要状态。查询已经发生后退款，记录实际事实并进入售后，不能恢复次数后自动再查。
- 资格检查、次数占用与任务创建需有统一事务/幂等规则。

业务尚未确定问答还是付费时，先完成手动测试和 Mock，不默认替用户开启真实付费自动化。

### 10.5 结果交付适配

先审查现有 `external_operation.py`、`realtime_delivery.py` 和手动消息发送回执的适用范围，再提取通用发送协调能力。不要把查询结果伪装成卡密库存。

保留平台消息确认、平台订单发货确认和本地记录成功三个不同事实。文字发出不能自动宣称订单已完成发货；若业务需要确认发货，应建立独立的授权和回执步骤。

完成条件：对一个明确商品，真实闭环的每个阶段都有可核对回执；模拟故障时不重复查询、不重复交付、不串买家。真实外部测试只在目标和预览内容得到明确授权后执行。

## 12. S07：打包、安装、备份和升级

### 12.1 打包顺序

1. 为桌面依赖建立独立锁定清单；不要无审查把服务器全部依赖打包。
2. 将 Vue 构建为静态资源，打包后不运行 Vite。
3. 采用 Python 目录式冻结构建作为首个打包原型，测量冷启动、体积和缺失依赖，再固定具体工具及版本。
4. 打包 pywebview 与必要 WebView2 检测/引导；私有 Runtime 的分发方式单独核实。
5. Crawler 确有需要时，使用私有 Node/浏览器组件并限制并发和生命周期；否则首版不启动。
6. QQ 组件仅在授权和数据边界核验通过后纳入分发。开发阶段独立运行不代表最终安装已完成。
7. 新增 `desktop/packaging/` 构建脚本和安装器配置，生成当前用户级安装包、快捷方式和卸载入口。

### 12.2 安装与进程管理

- 不改全局 PATH、不覆盖全局 Python/Node、不清理用户现有 QQ 数据。
- 子进程记录 PID、可执行文件和启动归属；退出时只停止本应用拥有的实例。
- 开机自启默认关闭；关闭窗口到托盘需要用户选择并有清楚提示。
- 单实例检查作用于实际数据目录，不能只锁窗口而允许第二个业务宿主写同库。

### 12.3 备份和更新

1. 使用 SQLite 一致性备份能力，不直接复制运行中的 `.db` 忽略 WAL。
2. 备份加密；跨电脑恢复采用用户主动提供的恢复密码/材料，不复制 DPAPI 封装就假定可用。
3. 升级前暂停派发、停止宿主、完成一致性备份并核对可用空间。
4. 新构建取得独占锁后迁移；失败保留原库与错误信息，不自动清空重建。
5. 回滚先核对数据库版本兼容；不兼容时恢复匹配备份，不能直接用旧程序打开新库。
6. 恢复旧备份仍可能重放已经发生的外部操作：恢复后默认暂停，核查备份之后的 QQ/闲鱼发送与事件缺口，再决定能否恢复自动业务。
7. 卸载区分保留/删除本应用数据，只作用于核对过的应用目录。

## 15. 实施过程中的明确边界

1. 不更换 Go，不迁移到 Pro，不复制整个 Tulpa 项目进主仓库。
2. 不把 `DB_PATH` 兼容字段当作已经存在 SQLite 支持的证据。
3. 不用 `APP_ENV=test/dev`、默认密钥或关闭认证使桌面“先跑起来”。
4. 不只隐藏前端菜单；服务端路由与后台生产者都必须裁剪。
5. 不将 HTTP 200、协程结束、文本“发送成功”当作平台最终确认。
6. 不提供任意 QQ 目标、任意 Action、任意 Shell/SQL 工具。
7. 不让 unknown 通过换请求编号或通用重试按钮重新发送。
8. 不把模拟器通过写成真实 QQ 可用，不把安装在开发电脑写成干净系统验收通过。
9. 不承诺换技术、限频或随机延迟能够消除平台账号风险。
10. 原计划中的发布门槛继续适用；未通过的项记录为未通过，不用文档措辞代替证据。

## 16. 当前结论与下一步入口

当前阶段是“基线已静态核对、实施方案已拆分”，不是桌面原型已完成。

接下来按以下顺序开始代码实施：

1. S00 核对开发解释器与工作区，建立分支和依赖清单。
2. C01 实现无外部副作用的契约、Mock、策略、匹配与测试。
3. C02/C03 建立桌面配置、SQLite、凭据和最小宿主。
4. C04 用持久化 Mock 证明任务与故障恢复正确。
5. 真实 QQ 契约核实后进入 C05，再与闲鱼适配组成第一条闭环。

真实接入前尚需补齐：机器人类型、一组脱敏请求/完整回复、请求关联/结束规则、允许用途与频率，以及问答或付款后交付的业务选择。这些信息不阻塞前面的 Mock 和桌面基础开发。
