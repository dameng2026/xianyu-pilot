# 开源版更新日志维护规则

> **强制规则**：任何 AI 模型在执行"上线/发布"动作前，必须先完整阅读本文件，并按本文件流程维护更新日志。
> 未经对比代码差异并更新 `CHANGELOG.md` 与 `apps/web/package.json` 的 `version`，不得执行上线。
> 本规则参考商业版 `release-notes-workflow.md`，适配开源版的技术栈与发布流程。

## 一、功能概述

开源版前台「关于我们 → 更新日志」板块用于向用户展示版本迭代与功能演进记录。

- **展示页面**：`apps/web/src/pages/about/AboutPage.vue`
- **数据源**：`CHANGELOG.md`（唯一权威数据源，最新版本在前）
- **版本号注入**：`apps/web/package.json` 的 `version` 字段 → Vite 注入 → 前台展示
- **当前版本展示**：「关于我们」页面顶部展示 `package.json` 的 `version` 作为"当前版本"

## 二、版本号递增规则（语义化版本 SemVer）

版本号格式 `MAJOR.MINOR.PATCH`（如 `1.4.0`），按本次上线的功能变动规模递增：

| 变动类型 | 触发条件 | 版本号递增 | 示例 |
|---------|---------|-----------|------|
| 问题修复 | bug 修复、文案微调、样式小修补 | 修订号 +1 | `1.4.0 → 1.4.1` |
| 功能更新 | 新增功能、功能优化升级、交互重构 | 次版本号 +1 | `1.4.0 → 1.5.0` |
| 大版本 | 大量功能改变、架构调整、不兼容更新 | 主版本号 +1 | `1.4.0 → 2.0.0` |

**判定优先级**：major > minor > patch。一次上线同时含多种变动时，按最高等级递增。例如同时有 bug 修复和新增功能，按 minor 递增。

**无功能变动不递增**：若本次上线仅修改文档、CI 配置等非功能性代码，不新增日志条目、不递增版本号。

## 三、CHANGELOG.md 结构规范

文件格式参考 [Keep a Changelog](https://keepachangelog.com/zh-CN/1.1.0/)，遵循以下结构：

```markdown
# 更新日志

（文件头说明，固定不变）

## [Unreleased]

### 新增
- **功能名称**：面向用户描述的功能变更

### 变更
- **变更名称**：面向用户描述的变更内容

### 优化
- **优化名称**：面向用户描述的优化内容

### 修复
- **修复名称**：面向用户描述的修复内容

## [v1.5.0] - 2026-07-26

### 新增
- ...

## [v1.4.0] - 2026-07-24

### 新增
- ...
```

**结构约束**：
1. 顶部必须保留一个 `## [Unreleased]` 段，用于收集尚未发布的变更
2. 每个正式版本段格式为 `## [vX.Y.Z] - YYYY-MM-DD`（带 `v` 前缀，日期为发布日）
3. 版本按时间倒序排列（最新在前）
4. 每个版本段下按需使用 `### 新增` / `### 变更` / `### 优化` / `### 修复` 分类
5. 每条变更以 `- **功能名称**：面向用户描述` 格式书写，**面向用户可感知的功能变动**，避免纯技术实现细节
6. 不得删除历史版本段，只追加

## 四、上线前代码对比与日志更新流程（强制）

### 4.1 对比方案：本地 git tag

开源版使用**本地 git tag** 标记每次上线点：

- 每次上线后打一个 `released/<版本号>` 的标签指向当时已上线的 commit
- 下次上线前对比「最新 released 标签」与「当前工作区」即可找出本次将上线的变动

### 4.2 每次上线前的对比与日志更新流程

```bash
# 步骤 1：找到最新已上线标签
LATEST_TAG=$(git tag --list 'released/*' --sort=-v:refname | head -1)
# 若为空，说明尚未建立基线，先打 released/1.0.0

# 步骤 2：对比代码差异
git diff $LATEST_TAG
```

**步骤 3：分析 diff，判定变动类型**

AI 需阅读 diff 输出，识别功能变动：
- 仅修复 bug / 文案 / 样式小修补 → `patch`
- 新增功能 / 功能优化升级 / 交互重构 → `minor`
- 大量功能改变 / 架构调整 → `major`
- 无功能变动 → 跳过日志更新，直接上线

**步骤 4：更新 CHANGELOG.md 与 package.json**

按判定结果：
1. 将 `## [Unreleased]` 段的内容转为 `## [vX.Y.Z] - YYYY-MM-DD`（今日日期）
2. 在文件顶部（`## [Unreleased]` 之前或之后）新增空的 `## [Unreleased]` 段
3. 同步更新 `apps/web/package.json` 的 `version` 字段为新版本号

**步骤 5：提交并打新标签**

```bash
git add CHANGELOG.md apps/web/package.json
git commit -m "chore(release): bump to <新版本号>"
git tag released/<新版本号>
```

**步骤 6：执行正式上线**

确认日志已更新且标签已打后，方可执行正式上线流程。

## 五、关于我们页面与更新日志的一致性

「关于我们」页面的"当前版本"来自 `apps/web/package.json` 的 `version` 字段，"更新日志"来自 `CHANGELOG.md` 的解析结果。二者必须保持一致：

1. `package.json` 的 `version` 必须等于 `CHANGELOG.md` 中最新正式版本段的版本号
2. 每次更新日志后必须同步检查 `package.json` 版本号
3. 「关于我们」页面的更新日志展示应完整显示所有历史版本（1.1.0、1.2.0、1.3.0、1.4.0、1.5.0 等），不得只显示最新版本

## 六、关键约束（违反即为 Bug）

1. **上线必须先更新日志**：未经对比代码差异并更新 `CHANGELOG.md` 与 `package.json`，不得执行上线
2. **版本号必须同步**：`CHANGELOG.md` 最新版本段与 `package.json` 的 `version` 必须一致
3. **日志必须面向用户**：每条变更描述用户可感知的功能变动，不写纯技术实现细节
4. **历史版本不可删除**：只追加新版本段，不得修改或删除已有版本段
5. **Unreleased 段必须保留**：每次发布后将 `[Unreleased]` 转为正式版本，并新增空 `[Unreleased]` 段
6. **关于我们页面必须显示完整日志**：所有历史版本（1.1.0+）都必须在关于我们页面可见
